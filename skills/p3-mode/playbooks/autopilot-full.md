### Autopilot-full

**Run a finite queue. The parent owns the queue, gates, and verdicts; each implementation owner owns one unit through its authorized landing.**

1. **Set the boundary.** Turn the requested work into a finite list of units, each with a goal and observable acceptance conditions. Keep unrelated improvements in a named backlog. Record operator-owned items and every approval or merge gate; a request for a plan is not approval. No unit leaves its gate without the operator's go.

2. **Prove the route before parallel work.** Read the project's verification skill and feature map for each affected user path. Use the existing app driver to reproduce and verify one end-to-end pilot, recording the real command or interaction and its result. If the route or driver is missing, establish it or report the exact gap before dispatching parallel owners. A local worktree is a separate checkout, not a separate machine; use the designated isolated app verifier for live app work.

3. **Start the watchdog before the first worker.** Call `list_scheduled_tasks`. Reuse only this run's enabled schedule already bound to the current parent thread; never move another thread's schedule or enable a disabled one without authorization. Otherwise create exactly one enabled `schedule_task` bound to this thread with `{type: "interval", everyMs: 120000}` and a stable per-run `clientRequestId`. Record its ID in the durable queue. Keep `run-state.json` beside that queue, initially `{"state":"running"}`. Completion events are the normal wake-up; the watchdog is fallback. On explicit pause, first persist `{"state":"paused"}`, then follow `playbooks/pause-safely.md`. Preserve the queue, receipts, enabled watchdog, and resume action. Delete only this run's watchdog when all scoped work is complete or the operator explicitly stops the run.

4. **Dispatch bounded work.** Start with one end-to-end pilot. For routine bounded work, use at most two implementation owners, one per independent unit, plus one designated isolated app verifier and one independent reviewer. Raise the cap only with explicit project or operator configuration after a successful pilot. Use a larger verification panel only when the change warrants it or the project requires it. Resolve each role from project-root `p3-models.md`, else `~/.agents/p3-models.md`, and apply current user overrides before selecting from `orchestrator_capabilities`; never hardcode model slugs. Delegate children with self-contained briefs via `delegate_task`, `mode: "async"`, and `isolation: "worktree"`. Do not create top-level threads for child work.

   Each unit's durable record names its goal, acceptance conditions, `taskId`, checkout, branch or PR, actual head SHA, current owner and next action, and review and gate receipts. Briefs identify the allowed scope, relevant feature-map path, verification route, and gates. Register each opened PR immediately with `link_pull_request`.

5. **Reconcile evidence, not claims.** Treat child completion notifications as normal; on every wake or watchdog tick, first read `run-state.json`. While paused, record incoming receipts but perform no recovery, dispatch, verification, or landing. Only explicit operator resume can restore `running`, after reconciling the checkpoint and live tasks. When running, reconcile the durable records with `task_status`, PR state, actual branch/head, and visible side effects before acting. Consume terminal results and perform the missing next action in the same turn. A statement of intent is not a completed action. Do not restart work because a tick arrived during an active turn, or interrupt a valid CI, review, or resource wait based only on age or a status label. Recover only a task with evidence of failure or stalling; record that evidence, confirm the old task is stopped, then send a fresh consolidated brief with prior receipts and the exact remaining work. Never duplicate an active owner or reviewer.

6. **Verify each code-ready unit.** The owner reports the committed head SHA and self-check receipts. At that head, the designated verifier, who did not write the code, uses the existing app driver to exercise the load-bearing behavior and records the command or interaction, observed result, and evidence. A fresh independent reviewer checks the patch and its acceptance conditions. For routine bounded changes these are one verifier and one reviewer, not a swarm. A verdict names the exact head and patch it covers. Re-run checks and live verification when behavior or relevant code changes; a new head needs its own green CI. Patch equivalence can carry a verdict only when `playbooks/shipping.md` permits it and the evidence still describes the code that will land. Green CI or prose alone is not behavioral verification.

7. **Resolve findings without losing them.** Send proven findings to the owner with the failing behavior and evidence. Keep a blocking bug open until a fresh reviewer verifies its fix. After repeated failure, consolidate the receipts and escalate to the parent or split the unit; never auto-clear or drop the blocker. Record unrelated improvements in the named backlog without enlarging the queue. Any proposed relaxation of a verification gate needs independent evidence and the parent's countersign before use; operator-owned gates still need the operator's authorization.

8. **Land only with authority and current evidence.** The owner prepares the merge result against current trunk and checks whether trunk changes affect the patch, following `playbooks/shipping.md`. Re-run affected checks and obtain a fresh verdict when the code that would land was not covered. The parent confirms the required user gate, reviewer receipt, current head, and green CI before the authorized merge. Never infer merge permission from a plan request or bypass a forge-enforced approval. Record the merged result and verify the PR state.

9. **Stop or hand back cleanly.** On explicit stop, halt dispatch, cancel active children, preserve the queue and receipts, and delete only this run's watchdog. If work remains when handing back, leave a real waiting event or enabled watchdog plus a durable next action; “I will do X” is not a handoff.

**Reply:** report each unit's goal, owner and task, actual head and PR state, verification and review receipts, completed gates, blockers, and the next action. Link PRs and the durable queue record.
