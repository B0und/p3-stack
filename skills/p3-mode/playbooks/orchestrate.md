### Orchestrate

**You own the program, queue, gates, and verdicts; each implementation owner owns one unit through its authorized landing.** Use this for work that outlives one agent session: many evolving units or stacked PRs, multi-day coordination, or a human checking in between runs. A finite list of features or PRs that fits a bounded queue belongs in [Autopilot-full](autopilot-full.md). One task driven to a predicate is Autonomous run. One ambitious run needing a bespoke workflow is figure-it-out. Work one agent could finish inside the session's budget is not a program.

The parent frames work, authors briefs, consumes completion events, dispatches the next action, keeps the human report, and makes judgment calls. It may inspect diffs and evidence to review work; code changes and conflicted merges are delegated. Mechanically landing a verified unit is bookkeeping only where `playbooks/shipping.md` and the required authorization allow it. Nothing in the store itself dispatches, waits, or wakes work.

#### Roles and placement

- **Coordinator (this thread).** Owns the queue, durable store, human gates, and program verdicts. Delegate implementation and fixes with `delegate_task`, `mode: "async"`, and `isolation: "worktree"`. Use `t3_thread_launch` only when the user explicitly asks for a new top-level conversation.
- **Track coordinator.** Add one only when the program exceeds what one parent can drain. It owns its track's units and briefs, and rolls up receipts at boundaries. Keep depth to coordinator, track, worker. A track the parent can drain needs no middle layer.
- **Implementation owner.** Owns one unit in one worktree through its authorized landing. One writer per worktree or branch. A worktree is a separate checkout, not a separate machine.
- **Verifier and reviewer.** Keep one designated isolated app verifier on a local machine for live app work; it must not have written the code. Use one independent reviewer for routine work. Do not assume worktree isolation provides machine or app-state isolation.

Default to at most two concurrent implementation owners, plus the designated verifier and reviewer as needed. Raise the cap only with explicit project or operator configuration, and only after a successful pilot demonstrates the route. Prefer fewer, broader workers. Resolve model roles in this order: project-root `p3-models.md`, `~/.agents/p3-models.md`, then the live `orchestrator_capabilities` catalog. Follow the current user's model override for this run. Never hardcode model IDs.

#### Durable store

Create `orchestrate/<project-slug>/` in the current project. Keep every file to one writer; owners publish facts and the coordinator aggregates them. Use plain TSV, JSON, and Markdown.

- `preferences.md` contains only nonduplicated, run-specific deltas and points to the authoritative project policy in `AGENTS.md`. Read that policy before dispatch. Do not copy its rules into preferences or paste stale preferences into every spawn. Briefs include relevant, current constraints and acceptance details; they do not copy obsolete gates or countermand `AGENTS.md`. Keep one source per rule.
- `overview.md` is the durable program and PR record. Append facts; do not rewrite it wholesale per event.
- `units.tsv` records each unit's id, track, state, goal, acceptance, owner, `taskId`, worktree, branch, PR, current PR head SHA, last gate and review receipts, and actual next action. Reconcile ownership against live tasks and heads before dispatch. Never assign a second writer while the previous owner may still be active.
- `frontier.json` records the computed merge frontier: ordered PRs, branches, head SHAs, generation, and lowest unmerged PR.
- `ledger.tsv` records each verification verdict keyed by PR and exact head SHA. `inbox/` stores completion pointers and evidence. `gates.md` records human decisions needed. `decisions.tsv` is the decision trail; derive `status.md` from the tables at each reconciliation.
- Record this run's watchdog schedule ID in the store. Do not claim prose enforces dispatch or wakes a thread: T3 completion events and the scheduler provide the route, the agent performs the action, and a live pilot must prove the route works.

#### Briefs and dispatch

Every child receives a self-contained brief because it cannot see parent context. Include goal, exclusive write scope, relevant paths and PRs, dependencies and upstream findings, observable acceptance, exact verification route, gates, forbidden actions, and report shape. Include only relevant policy constraints and run-specific preferences; link the authoritative project policy. A track brief also names its unit boundary, spawn budget, drain protocol, and rollup format. Missing scope or acceptance means the unit is not ready to dispatch.

Resolve track names per project; build, landing, and verification are common cuts, not required structure. Keep sibling communication upward. Relay relevant upstream reports into downstream briefs. Never resume-chain an old brief: recover with a fresh consolidated brief containing prior receipts and exact remaining work.

#### Steps

1. **Frame the program.** Define its completion predicate, tracks, expected units and stacks, human-owned actions, and gates. If the work is a finite list fitting a bounded queue, route to Autopilot-full. If one agent can carry the whole program, use Autonomous run instead. Present the framing once; proceed with reversible preparation. Route contested decomposition or a one-way door through the arena skill before the pilot.
2. **Set up the store and watchdog before the first worker.** Read current project `AGENTS.md` policy, create the store, open the trail with show-me-your-work, and seed `frontier.json` from existing PRs per Stack safety. Call `list_scheduled_tasks`. Reuse only this run's enabled schedule already bound to the current parent thread. Otherwise create exactly one enabled watchdog bound to this parent using `schedule_task` with the structured schedule `{type: "interval", everyMs: 120000}` and a stable per-run `clientRequestId`; record its returned ID. Never rebind another thread's schedule or enable a disabled old schedule. T3 child completion events are the normal wake; the watchdog is fallback.
3. **Pilot the route.** Read the project's verification skill and feature map for affected paths. Push one unit through brief, worker, verification, stack entry, ledger row, and merge. Record the actual driver command or interaction and result. If the route or driver is missing, establish it or report the exact gap before parallel dispatch. Fix the contract from pilot evidence. For near-identical cheap units, the first normal unit is the pilot; fan out once it lands. Use a dedicated audit gate only for expensive or novel unit shapes.
4. **Scale with a rolling queue.** Dispatch at most two implementation owners by default, one per independent unit, with `delegate_task` async worktree tasks. Increase only under explicit project or operator configuration after a successful pilot. Record each returned `taskId` and assign one durable owner per unit. Register every PR immediately with `link_pull_request`. Recompute ready work after each completion, relay upstream evidence, and keep the frontier green before upper-stack work. Never duplicate a live owner or reviewer.
5. **Consume completions and act in the same turn.** Treat T3 child completion events as normal wake-ups. On each event or watchdog tick, reconcile store records with `task_status`, PR state, actual branch and head, and visible side effects. For a terminal task, consume its result, update durable receipts, and dispatch or perform the actual next action before ending the turn: review, fix assignment, verification, authorized landing, or a specific legitimate wait. A critical section may finish first, but its follow-on obligations must be handled before ending the turn; do not park them for an unscheduled future batch. Do not rely on prose to guarantee wake-up.
6. **Recover only on evidence.** Distinguish a real awaited CI, review, or resource completion from a no-op wait. Timestamps alone do not prove a stall. Recover a known failed task using a fresh consolidated brief and its prior receipts. Do not start a second writer until the old task is confirmed stopped. Reconcile late or zombie results against the current owner, PR, and head before accepting them. Preserve unique findings through a fresh unit rather than blind merging.
7. **Verify and review at the current head.** The owner reports committed head SHA and self-check receipts. The designated isolated app verifier, who did not write the code, exercises load-bearing behavior with the existing app driver and records command or interaction, result, and evidence. A fresh independent reviewer checks the patch and acceptance conditions. Record the exact head and patch covered by each verdict. Re-run affected checks and live verification after relevant code changes; a new head needs its own green CI. Patch equivalence carries a verdict only when `playbooks/shipping.md` permits it and the evidence still describes the landing code. CI green or prose alone is not behavioral verification.
8. **Resolve findings and land with authority.** Keep reproduced bugs and acceptance failures blocking until a fresh reviewer verifies the fix. After repeated failure, consolidate evidence and escalate to the parent or split the unit; never auto-clear or drop the blocker. Put unrelated improvements in a named backlog. A proposed verification-gate relaxation needs independent evidence and the parent's countersign; operator-owned gates still need operator authorization. The owner prepares the merge result against current trunk per `playbooks/shipping.md`. The parent confirms required user authorization, current head, reviewer receipt, current verdict, and green CI before an authorized merge. Never infer merge permission from a plan request or bypass a forge-enforced approval. Record the merged result, verify PR state, and advance the frontier only on merge or reported new head SHAs.
9. **Pause, stop, or close cleanly.** On pause, preserve the queue, receipts, watchdog state, and exact resume action; do not disable or delete the schedule. On explicit stop, halt dispatch, cancel active children, preserve the queue and receipts, and delete only this run's watchdog. When all scoped work is complete, reconcile all tasks to terminal state, verify the predicate on the real artifact and every landed PR's current-head verdict, audit the trail per show-me-your-work including its cross-model review, encode recurring corrections in the brief template or nonduplicated preferences, and delete only this run's watchdog. Leave the store intact. When handing work back with units open, leave a real waiting event or enabled watchdog plus a durable next action.

#### Stack safety

- Recompute `frontier.json` from `gh` and `list_thread_pull_requests` after each merge and stack mutation; GitHub base refs can drift mid-restack. A PR missing from both sources is reported, never guessed.
- Exactly one stacker per stack may rebase or restack, serialized within its stack. Record its owner. Restacks run in the stacker's own worktree thread. Workers never rebase. Babysitters follow `playbooks/babysit.md`, one per stack and scoped to one immutable frontier generation; they report conflicts to the stacker.
- PR closes and retargets go through the stacker only. Closing a base PR orphans every chain above it. Merges and stack surgery are units with briefs like any other. One retro watcher follows merged PRs for reverts, post-merge CI breaks, and orphaned follow-ups.

#### Verification and liveness

Scale verification to the unit. For a single cheap command, the worker runs it and reports output; the coordinator checks receipts. Use the designated isolated app verifier for live app behavior and an independent reviewer for each routine unit. A verdict names PR and exact head SHA; new heads void old verdicts. CI green is an input, not a verdict. Behavioral work needs better than `type-check-only`; `verifier-blocked` is not a pass and must be retried when the environment heals. `verifier-failed` gets a fix unit, not a re-verify. A worker may self-report; the verifier overrides on the same key.

Never resume a task merely to check on it. Probe read-only using the store, `gh`, pushed branches, `task_status`, and `t3_thread_read`. A silent death gets a synthetic inbox row with unit, failure mode, last evidence, and options. Replan on evidence as it arrives; never wait for full quiescence. Retry cap-hit or oom with smaller scope; network drop as-is; tool error on a different resolved model; unknown once. After two retries, abandon the unit and replan. Bound infrastructure retries too; after repeated tool aborts, record a terminal handoff with exact resume action and end the run.

#### Escalation

Batch irreversible actions, genuine product or preference calls, contradictions between standing policy and observed reality, and program-level dead ends that survived a replan into `gates.md` before asking the human. Route work around open gates. Frontier nudges, rebase mechanics, retries, CI flake triage, review-thread triage, and scope forbidden by the brief stay with the coordinator. Mid-run discoveries fix only what blocks the frontier; park other improvements in follow-ups.

**Reply:** At checkpoints and close, report the predicate and counts from the durable tables, tracks and landed work, frontier PRs and SHAs, verification and review receipts, abandoned work and reasons, human gates, store path, trail path, and each unit's actual next action. Include PR links.
